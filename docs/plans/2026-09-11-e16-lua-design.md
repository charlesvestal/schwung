# E16 via Lua — design

Remote mode works and is not reliable. This is the alternative, and the reason
to take it is measured rather than aesthetic.

## Why leave remote mode

`docs/E16_REMOTE.md` has the full account. The short version: a framebuffer is
a **394-packet SysEx** that must cross four buffers intact, and every one of
them drops packets individually when full. Three truncations were found and two
fixed; the screen went from constantly garbled to occasionally garbled and no
further. Every pacing experiment contradicted the rate theory — pace 1 is bad,
12 is worse than 8, 20 wedged the device.

**A short message has none of that exposure.** Nothing on this path can split a
7-packet message the way it splits a 394-packet one.

Two other things fall out for free: the device draws with its own fonts and
layout, so the four-character LABELS ceiling disappears; and the repaint stops
being ours to schedule, so the settle/starve/priority machinery goes away.

## What the firmware actually provides

Lua 5.4 is embedded in E16 firmware 1.1.0. Enumerated from the decoded image
(`strings` over the unencrypted STM32 binary), not from documentation:

| kind | names |
|---|---|
| callbacks | `onInit`, `onEncoderTurn`, `onEncoderPress`, `onSysex`, `onPageChange`, `onVarChange`, `update` |
| output | `sendCC`, `sendPC`, `sendMidi`, `sendSysex` |
| display | `setTitle`, `resetTitle`, `setControls`, `setByIndex`, `updateByIndex`, `text`, `leds` |
| control | `setUpdateRate`, `getPage`, `register`, `slots`, `is_held`, `scaled` |

Release notes add: script variables persist with the scene, `update()` and
`led.update`/`updateByIndex` arrived in 1.1.0, and 1.1.0 "fixed rendering
issues dispatched by Lua".

## The one thing Lua does NOT fix

**`onSysex` is the only inbound host→script channel.** There is no `onMidi` or
`onCC` in the binding table, so the host still reaches the script by SysEx —
and Move's XMOS still cannot send SysEx to a multi-jack USB device. The 1-port
firmware patch (or OXI making the port count configurable) remains a
requirement.

That is worth stating plainly because it was the hoped-for win. Lua removes the
fragility and the 4-character limit; it does not remove the firmware
dependency.

## Shape

```
Schwung                                   E16 (Lua script, runs in a scene)
-------                                   ---------------------------------
page change  --> short SysEx: names   -->  setControls / setTitle
value change --> short SysEx: idx,val -->  setByIndex / updateByIndex
                                           renders natively, its own fonts
encoder turn <-- CC 1-16 (as today)   <--  onEncoderTurn -> sendCC
```

Sizes, against the 394-packet framebuffer: a 16-name page is ~150 bytes (~50
packets) and is sent only when the page changes; a value update is a handful of
bytes. Both are inside every buffer on the path with room to spare.

**No remote mode.** The script runs as an ordinary scene, so ENTER/ACK, the
presence lifecycle, the keepalive and the replug repaint all disappear — along
with the bugs each of them cost this week.

## What carries over, and what is deleted

Carried: `e16_map.mjs` (the slot/component model), the focus/follow logic in
`e16_surface.mjs`, `e16_input.mjs` (encoders still arrive as relative CC), and
the page planner integration — the hard-won parts.

Deleted: `e16_canvas.mjs`, `renderView`/`renderMap`, `framebufferMsg`, the
display pacing machinery, `SCREEN_STARVE_MS`, the pace file and its cap. The
transport fixes stay — they were general (`js_shadow_midi_send` atomicity, the
carry snapshot deferral) and benefit every module that sends MIDI.

## Open questions the spike must answer

1. What are the real signatures of `setControls` / `setByIndex` / `setTitle`?
   The names are known; the arguments are not.
2. Can a script set a per-encoder **name** (the 4-char ceiling is what killed
   LABELS — if the script has the same limit, this buys less than it looks).
3. What does `onSysex` hand the script, and is there a length limit?
4. How is a script installed and distributed — OXI App only, or is a scene file
   something we could ship?
5. Does a script coexist with normal scene behaviour, or take the device over?

## First step

A hello-world script loaded through the OXI App: `setTitle("SCHWUNG")`, sixteen
named controls, and an `onSysex` that changes one value. That answers 1-3 and
5 in one pass, and nothing else is worth designing until it does.
