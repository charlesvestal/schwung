# E16 surface — state, and the open lead

Session of 2026-09-09..11. Branch `e16-surface`, ~75 commits, 331 host tests
green, everything deployed to the device.

## Where it stands

The surface WORKS: slots, components, parameters, encoders, rings, the Shift
map, replug recovery. It is driven by **LABELS** (34 packets) rather than a
framebuffer (394), because the framebuffer garbled constantly.

**It still garbles occasionally, and the cause is not yet found.**

## The open lead — READ THIS FIRST

`shadow_inject_ui_midi_out()` in `src/host/shadow_midi.c`:

```c
int snapshot_len = midi_out_shm->write_idx;
memcpy(local_buf, midi_out_shm->buffer, copy_len);
__sync_synchronize();
midi_out_shm->write_idx = 0;
memset(midi_out_shm->buffer, 0, SHADOW_MIDI_OUT_BUFFER_SIZE);
```

`shadow_ui` is a **separate process**. If it writes a packet after the shim
reads `snapshot_len` and before that `memset`, the memset erases the bytes and
`write_idx = 0` discards the index — while `js_shadow_midi_send()` has already
returned **true**. The packet is gone, the sender believes it was sent, and no
counter anywhere can see it: JS counts it as sent, the shim never received it.

One lost packet inside a SysEx corrupts the whole message. The shim drains
~344x/sec and JS writes in bursts of up to 34 packets at ~60 Hz, so the window
is small and hit regularly under load — which matches "garbles when playing and
turning knobs rapidly" better than anything else found.

The existing comment ("Copy before resetting to avoid a race where the JS
process writes new data between our reset and memcpy") shows the race was
considered; the guard only covers half of it.

**Suggested fix: proper SPSC discipline.** The consumer must never write the
producer's region. Add `read_idx` (there is a spare `reserved[1]` byte, but it
needs to be uint16 — take it from the buffer or grow the struct, both mappers
use `sizeof`):

- shim consumes `[read_idx, write_idx)` and sets `read_idx = write_idx`;
  it never touches `write_idx` and never memsets
- JS appends at `write_idx`; when `read_idx == write_idx` it may reset both to
  0 before appending (producer owns the reset)

## Ruled out, with evidence

| suspect | verdict | how |
|---|---|---|
| SHM buffer overflow | clean | counter, 0 under load with positive control |
| carry overflow | clean | counter, 0 under load |
| mailbox slots / stranding | inconclusive→fixed | see below |
| foreign packets interleaving our SysEx | **innocent** | Move's MIDI out disabled -> still garbles |
| the E16 itself | **innocent** | 193 framebuffers from a Mac, flawless; then 145 more with 636 clock + 616 note + 506 pressure interleaved, still flawless |
| LED flush clobbering our slots | innocent | its in-place replace matches `0x9n` in byte 1; our SysEx payload is 7-bit, so it cannot match |
| message SIZE | **innocent** | 101-byte LABELS garbles too; loss is per-PACKET |

**Fixed along the way** (real bugs, all ours):

1. `js_shadow_midi_send` wrote packets one at a time and dropped individually
   when full — truncating a SysEx mid-message. Now all-or-nothing.
2. The carry did the same, one buffer along. Snapshots are now taken whole or
   deferred whole.
3. Sent packets were never cleared from the shadow MIDI_OUT and the
   post-transfer sync copies the output region BACK from hardware, so a packet
   could be transmitted twice when Move did not rewrite the region. A repeat
   corrupts a SysEx exactly as a drop does. Now cleared.

## Instrument lessons (all three cost real time)

- **A counter that only fires on failure cannot tell "clean" from "empty".**
  Three captures read as clean because nobody was turning a knob. Always
  capture a positive control — `ui-midi-out: N packet(s) placed` exists for
  this now.
- **`static` in a header is per-translation-unit.** `foreign`, `stranded` and
  `placed` were incremented in `shadow_midi.c` and read in `shim_worker.c`,
  so they reported zero forever — and nearly produced the conclusion "our side
  is provably clean, report it to the vendor". Pinned by
  `tests/host/test_outbound_counters_shared.sh`.
- **When an instrument reports something impossible, suspect the instrument.**
  A "5785-byte" message (longer than anything sent) was a saturated Bluetooth
  adapter merging messages, and was nearly reported as Move dropping packets.
- **The firmware image decoder was wrong for most of the session** — each
  block carries a checksum byte that is not image data. `strings` survives the
  shift, code does not. See `docs/E16_REMOTE.md`.
